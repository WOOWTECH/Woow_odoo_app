# Test Plan: Woow Odoo App

> **Date:** 2026-03-23 (last updated 2026-04-27)
> **Total Tests:** 178 unit tests + 39 device tests + ~30 production E2E tests + 1 standalone GPS clock-in = ~248 automated verifications
> **Framework:** JUnit 5 + MockK + Turbine (unit), uiautomator2 + JSON-RPC + Chrome DevTools Protocol (device + E2E)
> **Latest Verified Run:** 2026-04-27 — verify-on-device.py 39/39 PASS, e2e_15 PASS, e2e-production-test.py 21/30 PASS (see `docs/2026-04-27-e2e-suite-results.md`)
> **Run Command:** see §4 — multiple scripts, run in order

---

## 1. Why This Test Plan Exists

Every test answers: **"If a user does X, does Y happen correctly?"**

Tests are not written to check code exists — they verify behavior that matters to users. Each test class maps to a feature the user interacts with.

## 2. Test Classes & Intentions

### 2.1 LoginViewModelTest (29 tests)

**Why:** Login is the first thing every user does. If login fails silently, crashes, or accepts bad input, users can't use the app at all.

| Test Category | Count | What It Verifies (User Perspective) |
|---------------|-------|-------------------------------------|
| Initial state | 4 | App starts on SERVER_INFO step, fields empty, rememberMe defaults true |
| Field updates | 6 | Typing in server/database/username/password updates state, clears previous errors |
| Step navigation | 6 | Blank server URL blocked, blank database blocked, HTTP rejected, HTTPS accepted, bare domain accepted, validation order correct |
| Login validation | 2 | Blank username/password rejected before making network call |
| HTTPS handling | 2 | Bare domain auto-prefixed with `https://`, already-prefixed URL not doubled |
| Error mapping | 9 | All 8 AuthResult.ErrorType values mapped to user-readable messages + clearError works |

**How it tests:** Creates LoginViewModel with mocked AccountRepository. Calls methods like `updateServerUrl()`, `goToNextStep()`, `login()`. Asserts on `uiState` flow emissions using Turbine.

### 2.2 OdooJsonRpcClientTest (15 tests)

**Why:** This is the only HTTP client in the app. If it fails, authentication breaks, sessions break, everything breaks. It also enforces HTTPS — a security requirement.

| Test Category | Count | What It Verifies |
|---------------|-------|------------------|
| HTTPS enforcement | 2 | `http://` URL returns HTTPS_REQUIRED error, bare domain also rejected |
| Cookie management | 3 | Empty state returns null, clearCookies on unknown host is safe |
| Network errors | 1 | Unreachable host returns NETWORK_ERROR (not crash) |
| Host extraction | 2 | Extracts host from https:// and http:// URLs correctly |
| Data classes | 4 | JsonRpcRequest/Response/Error/ErrorData construct properly |
| Error types | 3 | All 8 ErrorType enum values exist and are distinct |

**How it tests:** Creates real OdooJsonRpcClient (no mock). Calls `authenticate()` with invalid URLs/hosts. Verifies returned `AuthResult` type and error codes.

### 2.3 SettingsViewModelTest (29 tests)

**Why:** Settings screen controls theme, language, security (app lock, biometric, PIN), and cache. Every setting change must reach the repository correctly.

| Test Category | Count | What It Verifies |
|---------------|-------|------------------|
| Init | 2 | Calculates cache size on creation, exposes settings flow |
| Theme color | 2 | `updateThemeColor("#FF0000")` reaches SettingsRepository with exact string |
| App lock | 2 | Enable/disable reaches repository |
| Biometric | 2 | Enable/disable reaches repository |
| PIN management | 3 | `setPin("1234")` returns true, invalid PIN returns false, removePin delegates |
| Language | 4 | All 4 AppLanguage values (SYSTEM, EN, zh-TW, zh-CN) reach repository |
| Theme mode | 3 | All 3 ThemeMode values (SYSTEM, LIGHT, DARK) reach repository |
| Cache clearing | 2 | Calls both `clearAppCache()` and `clearWebViewCache()`, updates size text |
| Cache formatting | 6 | Formats 0 B, 512 B, 1 KB, 2 KB, KB→MB boundary, 3 MB correctly |
| Reduce motion | 3 | Toggle reaches repository |

**How it tests:** Creates SettingsViewModel with mocked SettingsRepository + CacheRepository. Calls each method. Verifies delegation via `verify {}`.

### 2.4 AccountRepositoryTest (23 tests)

**Why:** Account management (create, switch, delete, logout) is the core of multi-account support. Getting this wrong means users lose access or see wrong data.

| Test Category | Count | What It Verifies |
|---------------|-------|------------------|
| Auth new account | 3 | Creates account, saves password encrypted, deactivates others first |
| Auth existing | 1 | Updates display name instead of creating duplicate |
| Auth failure | 2 | No account saved on failure, error propagated correctly |
| Switch account | 4 | Valid switch re-authenticates, not-found returns false, no password returns false, re-auth failure returns false |
| Logout | 4 | Clears cookies + password + deletes account, uses active when no ID, no-op when no account |
| Remove account | 2 | Removes password + deletes, does NOT clear cookies (unlike logout) |
| Session access | 4 | Host extraction from various URL formats |
| Count | 3 | Delegates to DAO |

**How it tests:** Creates AccountRepository with mocked AccountDao, EncryptedPrefs, OdooJsonRpcClient. Verifies exact call sequences (deactivate → insert → activate).

### 2.5 SettingsRepositoryPinTest (14 tests)

**Why:** PIN security protects the app. PBKDF2 migration from SHA-256 must work or existing users get locked out. Exponential lockout prevents brute force.

| Test Category | Count | What It Verifies |
|---------------|-------|------------------|
| PBKDF2 hash format | 1 | Hash contains ":" separator (salt:hash) |
| Random salt | 1 | Same PIN produces different hashes each time |
| PIN length | 2 | Too short (<4) and too long (>6) rejected |
| Verify correct | 1 | Correct PIN returns true |
| Verify wrong | 1 | Wrong PIN returns false |
| Legacy migration | 2 | Correct PIN migrates SHA-256→PBKDF2; wrong PIN does NOT migrate |
| No PIN set | 1 | Returns false without crash |
| Exponential lockout | 5 | 5 fails→30s, 10→5min, 15→30min, 20→1hr, 100→caps at 1hr |

### 2.6 AuthViewModelTest (8 tests)

**Why:** Auth lifecycle determines whether the biometric/PIN screen appears. Getting bg→fg wrong means the app is either always locked or never locked.

| Test Category | Count | What It Verifies |
|---------------|-------|------------------|
| Default state | 1 | isAuthenticated starts false |
| Set authenticated | 1 | setAuthenticated(true) updates flow |
| bg→fg with lock ON | 1 | onAppBackgrounded() resets isAuthenticated |
| bg→fg with lock OFF | 1 | onAppBackgrounded() does NOT reset |
| PIN verify | 2 | Delegates to SettingsRepository (correct/wrong) |
| Lockout | 2 | getRemainingAttempts and isLockedOut delegate correctly |

### 2.7 DeepLinkValidatorTest (13 tests)

**Why:** Deep link injection is a CRITICAL security risk. Malicious apps can send `javascript:alert()` or `data:text/html` URLs. Every dangerous scheme must be blocked.

| Test Category | Count | What It Verifies |
|---------------|-------|------------------|
| Malicious URLs | 6 | javascript:, JAVASCRIPT:, data:, DATA:, empty, blank — all rejected |
| Valid paths | 4 | /web#id=42, /web#action=contacts, /web/login, /web — all accepted |
| External hosts | 3 | evil.com, attacker.com, ftp:// — all rejected |

### 2.8 DeepLinkManagerTest (5 tests)

**Why:** If the deep link is lost during auth flow, user taps notification → authenticates → sees home screen instead of the record they wanted.

| Test | What It Verifies |
|------|------------------|
| No pending | consume() returns null |
| Set + consume | Returns URL then clears |
| Set null | Clears pending |
| Flow | Emits changes reactively |
| Overwrite | Latest URL wins |

### 2.9 NotificationHelperTest (15 tests)

**Why:** Push notifications are the app's main new feature. Incorrect FLAG_IMMUTABLE crashes on Android 12+. Missing VISIBILITY_PRIVATE leaks business data on lock screen.

| Test Category | Count | What It Verifies |
|---------------|-------|------------------|
| Constants | 2 | EXTRA_ACTION_URL matches FCM key, CHANNEL_ID correct |
| Grouping | 7 | chatter/discuss/mention/activity produce correct groups, null falls back, empty string used as-is |
| Parameters | 3 | actionUrl and eventType are nullable |
| Security | 3 | FLAG_IMMUTABLE (0x04000000), VISIBILITY_PRIVATE (-1), FLAG_ACTIVITY_NEW_TASK | CLEAR_TOP |

### 2.10 WoowFcmServiceTest (20 tests)

**Why:** FCM data payload parsing must be exact. If "title" key is missing, no notification should show (not a crash). If keys are case-wrong ("Title" vs "title"), the message is silently dropped.

| Test Category | Count | What It Verifies |
|---------------|-------|------------------|
| Full payload | 2 | All 6 data fields extracted correctly |
| Partial payload | 3 | Missing optional fields pass null |
| Missing required | 5 | No title/body/data → no notification (no crash) |
| Edge cases | 5 | Empty strings, unicode, long body, complex URLs, extra keys ignored |
| Data key contract | 5 | Case sensitivity (title vs Title), exact key names |

### 2.11 CacheRepositoryTest (3 tests)

**Why:** Cache clearing must not delete login session or user settings.

| Test | What It Verifies |
|------|------------------|
| Clear with files | Directory emptied |
| Empty cache size | Returns 0 |
| Known files size | Returns exact byte count |

### 2.12 FcmTokenRepositoryTest (4 tests)

**Why:** FCM token must be stored encrypted and registered with ALL Odoo accounts (multi-account support).

| Test | What It Verifies |
|------|------------------|
| 3 accounts | Token stored + registered 3 times |
| 0 accounts | Token stored only, no error |
| Get stored | Returns saved token |
| Get null | Returns null when empty |

## 4. How to Run

```bash
# Step 1: Unit tests (no device needed, ~5 seconds)
./gradlew testDebugUnitTest
# Expected: 178 tests, 0 failures

# Step 2: Build and install
./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk

# Step 3: Login (manual, once per tunnel rotation)
# Update scripts/test_config.py:ODOO_URL or .env.test ODOO_URL=… then drive
# the Add Account flow with the live cloudflared URL.

# Step 4: Device verification (~10 min)
python3 scripts/verify-on-device.py
# Expected: 39 checks, 0 failures (V05 + V26 fixed in commit f0ccc98)

# Step 5: Geolocation clock-in (~2 min) — source of truth for E2E-15
python3 scripts/e2e_15_clockin_full.py
# Expected: PASS — creates hr.attendance with non-zero GPS

# Step 6: Production E2E (~15 min)
python3 scripts/e2e-production-test.py
# Latest run (2026-04-27): 21/30 PASS — see §6 Known Incomplete

# Step 7: Generate visual verification report (optional, ~20 min)
python3 scripts/e2e-verification-report.py
# Writes docs/verification-report/verification-report.md with screenshots
```

### Prerequisites (codified in `docs/2026-04-27-e2e-suite-results.md`)

1. Phone connected via USB with USB debugging enabled
2. `pip3 install uiautomator2 google-auth requests websocket-client playwright`
3. Odoo Docker running on `localhost:8069` (or set `ODOO_URL` env var)
4. cloudflared tunnel active: `cloudflared tunnel --url http://127.0.0.1:8069`
   then update `scripts/test_config.py:ODOO_URL` (single source of truth — see CLAUDE.md hard rule)
5. `app/google-services.json` with both `io.woowtech.odoo` and `io.woowtech.odoo.debug`
6. `app/firebase-service-account.json` (gitignored — copy from a sibling
   checkout if missing; needed for V20 + E2E-01..05/10/11/12/13)
7. `app/firebase-service-account.json` is set as `FIREBASE_SA_FILE` in `test_config.py`
8. App installed and logged in to the live tunnel URL
9. `pm grant POST_NOTIFICATIONS / ACCESS_FINE_LOCATION / ACCESS_COARSE_LOCATION` —
   the e2e-production-test.py script re-grants these at setup, but
   `verify-on-device.py` expects them at start.

that PASSES on the same device with the same code:

| Failed E2E (script issue) | Passing V-test (same product feature) |
